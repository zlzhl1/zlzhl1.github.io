员工想问一个问题，实际却可能先遇到安装、模型配置、账号和历史记录四个问题。做企业 AI 客户端时，我首先要解决的是让这些环节接起来，让用户能稳定地继续上一段工作。

我选择 OpenClaw 作为 Agent 基座，完成客户端及模型跳板初版的封装开发，随后与团队一起迭代。本文总结我负责的架构和工程增量；上游 Agent 能力、模型能力，以及团队后续的全部实现，都有各自的来源。

## OpenClaw 在这里承担什么

[OpenClaw](https://github.com/openclaw/openclaw) 提供个人 AI 助手及 Gateway 等基础设施。我把它理解为可复用的执行底座：围绕会话组织模型与工具调用，而产品仍需要补上面向实际用户的安装、身份、入口与故障处理。

在我的项目里，主要调用链可以简化为：

```text
员工操作
  → 桌面客户端与会话状态
  → 身份校验、模型接入与 Gateway 请求调度
  → Agent 的模型和工具调用
  → 事件回传、本地记录与界面更新
```

这里的箭头是职责关系，不代表这些部分共用一个进程，也不代表所有系统已经组成一个原子事务。

## 我为什么没有直接把聊天界面包起来

一个聊天界面能发消息，只解决了最前面的一小段。真正使用后，问题会集中出现在边界上：员工身份是否有效、模型是否可达、后台同步是否影响发送、界面展示的历史是否完整。

| 遇到的问题 | 我的设计与实现 | 要保留的判断 |
| --- | --- | --- |
| 模型入口与员工身份分散 | 统一客户端入口、模型接入和 OA 鉴权衔接 | 鉴权成功与模型服务可用要分别判断 |
| 健康检查、历史读取挤占聊天 | 在统一 RPC 入口分类调度，分开并发、队列和超时 | 后台任务失败不应直接变成聊天整体不可用 |
| 远端历史慢或暂时失败 | 本地优先展示，再静默补齐远端 | 缓存需要来源与刷新规则 |
| 多来源消息重复、乱序 | 统一会话事件与投影，增加持久化补偿队列 | 可恢复不等于任意故障都零丢失 |

这些改动可以在我参与阶段的提交与项目记录中对应到具体模块。后续团队又加入新的调度通道与状态批处理机制，介绍演进时需要分开归属。

## 一个很具体的取舍：后台任务能否让路

历史读取、健康探测和技能查询都很有用，但用户正在发送消息时，它们的紧迫程度不同。如果共用一个并发池，几个慢请求就可能让聊天排队。

我当时将请求分为实时、交互读取和后台三类，为各类设置自己的门禁与等待策略，并在聊天活跃时让后台让路。目的不是让所有任务都更快，而是先保护用户正在等待的交互。

这里也有成本：后台可能更晚完成，所以必须有可观察的等待、失败和恢复状态。简单提高全局并发，会把压力转移给模型、网络和本地数据库，未必能解决拥塞。

## 做完之后，我对“接入开源项目”的理解

最大的工作量往往出现在框架和使用场景之间。框架负责能力，产品工程负责把能力组织成稳定的体验：谁可以调用、哪个请求先处理、数据由谁写、失败后从哪里恢复。

我现在介绍这类项目，会先讲具体问题和修改的边界，再讲技术栈。仅列 Electron、React、OpenClaw 和 SQLite，很难说明我实际解决了什么。

这里不引用未经同环境重测的延迟或稳定性提升比例。历史记录能支持具体实现与取舍，生产效果还需要对应时间窗口的监控和用户反馈。
