客户端里有一种故障很容易被归咎于模型：用户点击发送后迟迟没有响应，但模型服务本身并没有失效。请求可能只是被历史读取、健康检查和其他后台任务挡在了前面。

我在企业 Agent 客户端中实现过请求分类调度、本地历史改造，以及会话事件和补偿队列相关模块。这里按我的历史实现说明设计，后续团队加入的状态批处理等机制单独看待。

## 先找到竞争发生在哪里

多个功能最终进入同一个 Gateway RPC 入口。如果它们共用并发门禁，一批慢读取会占住资源；如果后台失败又被提升为全局故障，界面会把“某个辅助操作失败”误报成“整个服务不可用”。

我的处理是按用户等待的紧迫程度分类：

| 类别 | 例子 | 调度意图 |
| --- | --- | --- |
| 实时 | 发送与正在进行的聊天交互 | 优先保护交互响应 |
| 交互读取 | 用户主动打开历史等 | 独立排队、并发与超时 |
| 后台 | 健康探测、定期同步等 | 聊天活跃时让路，失败独立记录 |

提高全局并发不能替代分类。它可能让数据库或上游服务承受更多压力，而用户交互仍没有明确保障。团队后续又将长轮询放入独立通道，这是方案演进，不是我最初三类实现的一部分。

## 本地优先也要解决“新回复被旧快照覆盖”

远端历史慢，我先用本地结果展示，再静默补齐。但如果补齐结果直接替换当前消息列表，用户刚收到的流式回复可能消失。

我围绕 JSONL 最近窗口、SQLite 按需导入、本地落库确认后刷新等机制，保护正在生成的消息。随后通过统一会话事件、消息身份和投影，把重复与乱序问题集中处理。

事件投影可以理解成：保留一串“发生了什么”，再按规则生成“当前该展示什么”。如果来源包含 capture、历史导入和远端回填，就需要稳定的去重身份及顺序规则。

## Outbox 解决的是失败后有处可找

我参与实现的持久化 Outbox 使用任务类型与去重键登记任务，领取时原子地改成处理中，失败后退避重试，多次失败再进入死信状态。

```text
登记任务 → 到期领取 → 执行 → 成功确认
                         └→ 退避重试 → 达到策略边界后保留死信
```

它让上传、修复和失败捕获有统一的恢复入口。重要的是，队列要能解释为什么等待、重试了几次，以及需要什么人工动作。

## 我后来专门核对了一次事务边界

代码中，消息写入和事件投影更新有自己的 SQLite 事务；上传入队发生在消息写入返回之后。两者没有共同的外层事务。

这意味着消息写入成功后、上传入队前，仍可能存在故障窗口。队列内部的原子领取、幂等和重试，不能消除这个窗口。因此我用“持久化补偿队列”描述已有能力，不使用严格 Transactional Outbox 或 exactly-once 来概括它。

如果下一步要补强，就需要明确是否把业务写入与待发任务放入同一数据库事务，再设计重复消费和修复检查。这是后续改造方向，不是已经完成的保证。

## 我的总结

稳定性问题通常不是某一个组件单独造成的。请求是否先被排队、界面是否展示旧状态、数据是否落库、补偿是否登记，需要沿真实调用顺序检查。

我现在更习惯用一次操作的生命周期讲架构：从点击到收到结果，再到失败和重开客户端。这样更容易发现“某个模块看起来可靠，但模块之间还有空隙”的问题。
