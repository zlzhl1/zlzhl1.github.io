设计一个 AI 功能时，可以先问：任务的主要路径能不能提前写清楚？

下面三个假设场景，分别对应不同的组织方式。

## 一件边界清楚的小事

“把这段会议记录整理成三条要点。”输入已经给出，输出要求也比较明确，可以先尝试一次普通模型调用。

此时更值得检查的是：原文是否完整，输出格式是否清楚，结果有没有遗漏。任务能用简单方式完成，就先围绕这条路径改善质量。

## 一串能提前规定的步骤

假设要把一份申请整理成待审核记录，可以把流程写成：

1. 提取申请信息。
2. 检查必填字段，缺少时补问。
3. 按规则校验数据。
4. 生成摘要，交给人工确认。

这适合用工作流组织。模型可以参与信息理解和文字生成，程序负责规定主要步骤、分支和检查条件。调用多次模型，也可以属于工作流。

## 下一步取决于刚找到的结果

再假设要调查一个陌生领域：开始时并不知道资料是否充分，也不知道需要补查哪些问题。

如果让模型读取当前结果，再决定查询什么、使用哪个工具、是否继续探索，就进入了 Agent 的组织方式。系统需要接收工具返回的实际结果，并在循环中判断进度。

## 用这张表检查自己的需求

| 组织方式 | 主要路径 | 更需要关注什么 |
| --- | --- | --- |
| 普通模型调用 | 输入到输出较直接 | 上下文、输出要求和结果质量 |
| 工作流 | 主要步骤由程序规定 | 分支条件、数据校验和异常处理 |
| Agent | 模型动态选择过程与工具 | 工具反馈、行动边界和停止条件 |

这里的区分参考了 Anthropic 对工作流与 Agent 的架构描述。具体系统可以组合使用这些方式，例如固定流程中包含一个负责资料探索的 Agent。[参考原文](https://www.anthropic.com/research/building-effective-agents)

## 增加自主性之前，先想清楚验收

灵活性会带来更多可能路径，也增加时间、成本和排查难度。可以先给任务写三类例子：正常输入、信息不足、工具失败，再观察不同方案如何处理。

同时明确完成条件、最多尝试次数，以及哪些动作需要程序校验或人工确认。模型能够输出一个工具调用，只代表它提出了行动；真实执行前，系统仍要检查参数、权限与当前状态。

选择方式时，先把任务、检查方法和失败出口写清楚，会比先选一个框架更容易推进。
