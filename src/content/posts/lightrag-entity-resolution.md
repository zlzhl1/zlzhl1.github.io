把文档变成图谱后，一个常见问题是：同一个部门在不同资料里有简称和全称，图里长成了多个节点；另一个问题恰好相反，名字接近的两个对象被合成了一个。

我基于 [LightRAG](https://github.com/HKUDS/LightRAG) 搭建图谱与向量知识服务，参与检索和后续数据工作流的衔接，重点实现过实体归一与抽取提示词管理。LightRAG 的抽取、图谱检索及切分能力来自开源与协作实现，我的增量主要针对企业资料里的歧义和可维护性。

## 先理解它解决哪一层问题

传统向量检索可以寻找相似文本。图谱增加了实体及关系，使问题能够围绕“对象之间有什么联系”组织上下文。实际链路仍要经过解析、切块、抽取、索引、检索与生成；建出节点并不能直接保证答案正确。

我的关注点在抽取结果进入图之前：如果实体身份已经混乱，后续检索再精细，也可能沿着错误节点找到一串看似合理的关系。

## 为什么先按类型召回，再比较名字

下面是构造案例，不是企业原文：

| 抽取名称 | 类型 | 可能的问题 |
| --- | --- | --- |
| 星河研发部 | 部门 | 与“星河研发中心”可能是同一对象，也可能不是 |
| 星河 | 品牌 | 名字相似，但不应该与部门自动合并 |
| 星河研发一部 | 部门 | 与研发部很接近，却可能有独立职责 |

如果先从所有类型里取 Top-K，再过滤类型，候选名额可能已被品牌或产品占满，真正的同类型对象根本没有被召回。因此我的实现把同类型约束放到向量召回前，再检查图节点是否存在、类型是否一致、相似度是否有效。

## 最高分还不够，要看第二名

只有最高相似度阈值，难以识别“两个候选都很像”。我增加了第一与第二候选的分差判断。下面是逻辑示意，阈值要用自己的标注样本校准，不能直接作为默认生产参数：

```python
def decide(top1, top2, threshold, min_margin):
    if top1 is None or top1.score < threshold:
        return "keep_new", "low_similarity"
    if top2 is not None and top1.score - top2.score < min_margin:
        return "keep_new", "ambiguous_candidates"
    return "merge", top1.entity_id
```

缺类型、类型冲突、低分和歧义都保留原对象及原因。这样会留下部分重复节点，但能避免用一个不确定的合并，把两个对象的关系永久混在一起。后续人工复核有了明确入口。

## 合并的是图结构，不只是名字

确定归一后，还需要同步实体键与关系端点、移除新产生的自环、合并相同端点关系。我把归一放在文档锚点写入前，并在真实图写入后再同步名称索引。

图存储和名称向量索引并没有因此成为一个跨存储事务。候选读取仍要检查图节点存在性，更新和删除也要维护索引。这个细节让我意识到：算法上的“合并成功”和系统里的“一致性完成”，需要分别设计。

## 规则会变，缓存身份也必须跟着变

另一个实际问题是提示词改了，结果却仍来自旧缓存。我将抽取提示词做成草稿、发布、版本检查和历史记录，并把有效提示词的 SHA-256 纳入缓存身份。

目的有两个：并发修改时避免互相覆盖；复盘某次抽取时，能够找回当时真正生效的规则。仅保存前端编辑框里的最新文字，解释不了历史结果。

## 目前能得到什么结论

这些实现支持类型过滤、分差保留、关系同步和策略追溯。现有记录没有提供真实业务误合并率的严格前后对照，所以我不会填写“精度提升多少”。下一步应建立包含异名、近名、同名异类型的标注集，分别测误合并与漏合并，再观察检索答案受影响的程度。

我最大的发现是：知识图谱需要允许“暂时无法确定”。把所有近似名称强行归一，可能让图更整齐，却使证据更不可信。
